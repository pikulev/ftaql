# Контракт системы анализа кода

Статус: проект спецификации 0.1 для обсуждения. Описанные ниже требования задают целевое поведение; они ещё не означают, что FtaQl или другие сборщики им соответствуют. Документ подготовлен на русском для внутренней работы.

Система анализа кода объединяет результаты независимых сборщиков в данные, пригодные для корпоративной аналитики. Каждый сборщик понимает свой стек, а общий контракт определяет смысл и форму публикуемых результатов. FtaQl выступает одной из реализаций для TypeScript и JavaScript.

Компания настраивает дополнительные измерения запуска через профиль данных. Из общего контракта, возможностей сборщика и этого профиля формируется итоговая схема. По этой схеме внешние инструменты забирают результаты и доставляют их в выбранные компанией хранилища.

Изменения текущего FtaQl описаны отдельно в [плане приведения FtaQl к контракту](../ftaql-contract-adoption/ru.md). Общая спецификация должна оставаться достаточной для автора другого сборщика без знакомства с исходниками FtaQl.

## Ответственность участников

| Участник | Ответственность |
| --- | --- |
| Общий контракт | Модель результатов, определения обязательных полей, правила расширения, построения схемы, идентификации и публикации |
| Профиль компании | Дополнительные измерения, их типы, обязательность, источники значений и размещение в выходных таблицах |
| Сборщик | Анализ конкретного стека, объявление возможностей и методик, формирование результатов и диагностики |
| Средства публикации компании | Перенос готового результата в доступное потребителю место, управление доступом и сроком хранения |
| Инструмент доставки | Чтение опубликованных данных, состояние загрузки, повторы и преобразование для целевого хранилища |
| Хранилище и BI | История, запросы, объединение с другими данными и представление результатов |

Термин «провайдер интеграции» далее означает внешний инструмент доставки, например Airbyte, Fivetran или конвейер на dlt. Сборщик является источником аналитических данных для такой интеграции.

Общий контракт не предписывает язык реализации, парсер, внутреннее AST, структуру репозитория или общий процесс исполнения. SDK может помогать формировать данные, но соответствие определяется наблюдаемым результатом и проверками, а не использованием SDK.

## Состав спецификации

Контракт разделён на три связанные части:

1. Семантическая модель объясняет, что означают запуск, сущность, измерение, связь и полнота результата.
2. Правила конфигурации определяют, как возможности сборщика и профиль компании преобразуются в схему.
3. Профиль публикации определяет физическое представление, проверку завершения и повторное чтение данных.

Для первой версии предлагается файловый профиль JSONL. Другие профили могут использовать ту же семантическую модель, если сохраняют её типы, ключи и состояния. Протоколы конкретных инструментов доставки оформляются отдельными интеграциями.

Слова «должен» и «обязан» обозначают требования проекта контракта. Вопросы, отложенные до стабилизации первой версии, перечислены в конце документа.

## Объявление возможностей сборщика

До анализа сборщик должен предоставлять машиночитаемое описание своих возможностей. Оно содержит идентификатор и версию сборщика, поддерживаемые версии контракта, языки, виды сущностей, определения метрик, виды связей и профили публикации.

Описание также указывает требования к входным данным: достаточно ли исходных файлов или необходимы конфигурация сборки, зависимости и инструменты стека. Возможности анализа проекта и отдельного файла объявляются раздельно.

Наличие метрики в описании означает поддержку её методики. Возможность вычислить её в конкретном запуске отражается в результате этого запуска. Например, отсутствие зависимостей проекта может ограничить разрешение ссылок, сохранив возможность вычислить локальные метрики.

Для согласованных метрик используются общие идентификаторы с закреплённой семантикой. Собственные метрики сборщик публикует в своём пространстве имён. Совпадение названий не является основанием считать разные методики эквивалентными.

## Логическая модель данных

Ниже заданы предлагаемые наборы записей. Каждый опубликованный набор сопровождается схемой с типами, обязательностью и ключами.

| Набор | Одна запись описывает | Ключ |
| --- | --- | --- |
| `runs` | Один запуск одного сборщика в объявленной области анализа | `run_id` |
| `entities` | Сущность, обнаруженную в этом запуске | `run_id`, `entity_id` |
| `metric_definitions` | Одну версию методики измерения | `metric_id`, `definition_version` |
| `measurements` | Результат одной методики для одной сущности | `run_id`, `entity_id`, `metric_id`, `definition_version` |
| `relations` | Одну агрегированную связь между сущностями или неразрешённую ссылку | `run_id`, `relation_id` |
| `cycles` | Цикл в графе с объявленной семантикой | `run_id`, `graph_kind`, `cycle_id` |
| `cycle_members` | Участие сущности в цикле | `run_id`, `graph_kind`, `cycle_id`, `entity_id` |
| `diagnostics` | Одно сообщение о качестве или ограничении анализа | `run_id`, `diagnostic_id` |

В первой версии обязательны `runs`, `entities`, `metric_definitions`, `measurements` и `diagnostics`. Дополнительные наборы объявляются по возможностям сборщика. Обязательный набор может быть пустым; его схема и число записей всё равно присутствуют в манифесте. Отсутствие неподдерживаемого набора отличается от пустого поддерживаемого набора.

### Запуск и область анализа

Запись `runs` содержит `run_id`, версию контракта, `schema_id`, `profile_id`, версию профиля, `project_id`, идентификатор и версию сборщика, время начала и окончания в UTC, состояние анализа и сведения о полноте. Ревизия и метка ветки или тега могут отсутствовать, но их отсутствие должно быть явным.

Область анализа описывает корни внутри проекта, фильтры файлов, выбранные модули и конфигурацию сборки. Вместе с ней сохраняются параметры, влияющие на метрики, и их отпечаток. Профиль экспортируемых данных имеет отдельную идентичность: смена корпоративного тега не означает смену методики анализа.

Если исходники отличаются от заявленной ревизии, это отражается в метаданных. Сборщик должен анализировать согласованный снимок входных данных либо сообщать, что согласованность не подтверждена. Изменение файлов между проходами нельзя выдавать за гарантированно воспроизводимый анализ одной ревизии.

Локальный абсолютный путь допустим как дополнительная диагностика, но не служит идентификатором проекта. Общая схема не требует публиковать исходный код, содержимое окружения или учётные данные.

### Сущности и связи

Сущность содержит `entity_id`, `kind`, язык, при необходимости относительный путь, родительскую сущность и состояние обработки. Поддерживаемые виды могут включать файл, функцию, тип, пакет и модуль. Сборщик публикует только те уровни, которые действительно анализирует.

Идентификатор сущности имеет документированное правило построения. Для файлов допустим путь относительно корня проекта с разделителем `/` и сохранением регистра. При таком правиле переименование меняет идентичность; автоматическое сопоставление переименований не входит в базовый контракт. Идентификатор из обхода AST без гарантий устойчивости нельзя объявлять стабильным между запусками.

Разрешённая связь ссылается на сущности через пары `run_id` и `entity_id`. Внешняя цель может быть описана отдельной внешней сущностью. Неразрешённая ссылка сохраняет исходное обозначение цели и состояние разрешения; отсутствие целевой сущности не превращает её в разрешённую связь.

Вид связи, условия её активности, уровень графа и методика вычисления веса должны быть описаны. Импорт пакета не преобразуется автоматически в связи со всеми его файлами. Представления графов вроде `all` и `runtime` имеют определение в возможностях сборщика, а их сопоставимость между стеками требует общей методики.

Идентификаторы циклов обязаны быть устойчивыми при повторном чтении одного артефакта. Устойчивость между запусками не предполагается. Участники цикла ссылаются на сущности по ключам, без индексов во внутренних массивах сборщика.

### Метрики и результаты измерений

Определение метрики содержит идентификатор, версию методики, описание, тип результата, единицу измерения, применимые виды сущностей и правила агрегации. Для производной оценки указываются формула и её версия. Общая формула не отменяет различий в правилах получения исходных счётчиков.

В первой версии измерения числовые. Запись содержит `status`, `integer_value`, `number_value` и при необходимости `diagnostic_id`. При `status = available` заполнено ровно одно поле значения, соответствующее определению метрики. Для остальных состояний оба поля равны `null`.

Предлагаемые состояния измерения: `available`, `not_applicable`, `unavailable` и `error`. Неподдерживаемые методики отсутствуют в возможностях сборщика. Для объявленных методик ожидаемое множество измерений определяется видом сущности, областью анализа и настройками выбора метрик; каждый ожидаемый результат должен иметь явное состояние.

Ноль означает вычисленное нулевое значение. `NaN` и бесконечности не допускаются: вместо них публикуется состояние ошибки вычисления с диагностикой. Для целых чисел предлагается знаковый 64-битный диапазон, для вещественных — конечные значения двойной точности. Интеграция обязана учитывать точность целых чисел при преобразовании типов.

Методика также определяет допустимость суммирования или усреднения. Например, сумму количеств уникальных операндов файлов нельзя объявлять количеством уникальных операндов проекта.

## Корпоративный профиль и построение схемы

Компания задаёт собственные измерения запуска: команду, продукт, подразделение, окружение, тип проверки и другие признаки. Эти измерения становятся типизированными полями итоговой схемы. Профиль описывает и поля, и правила получения значений, поэтому их не приходится угадывать по первой записи.

Предлагаемый пример самостоятельного профиля:

```json
{
  "profile_id": "company-code-quality",
  "profile_version": "1",
  "contract_version": "1.0",
  "run_dimensions": {
    "team": {
      "type": "string",
      "required": true,
      "min_length": 1,
      "source": { "env": "TEAM_NAME" }
    },
    "product": {
      "type": "string",
      "required": true,
      "source": { "value": "payments" }
    },
    "run_kind": {
      "type": "string",
      "required": true,
      "enum": ["pull_request", "scheduled", "manual"],
      "source": { "env": "ANALYSIS_RUN_KIND" }
    },
    "pull_request_number": {
      "type": "integer",
      "required": false,
      "source": { "env": "PR_NUMBER" }
    }
  },
  "publication": {
    "format": "jsonl",
    "repeat_run_dimensions": {
      "measurements": ["team", "product"]
    }
  }
}
```

Версия `1.0` в примере обозначает предполагаемую первую стабильную версию контракта. Сам формат профиля пока является проектом.

В таблице `runs` этот профиль создаёт колонки `dim_team`, `dim_product`, `dim_run_kind` и `dim_pull_request_number`. В `measurements` дополнительно появляются `dim_team` и `dim_product`. У повторённых полей совпадают типы и значения с записью запуска; внешний валидатор проверяет это равенство.

| Поле итоговой схемы | Тип | Допускает `null` | Размещение |
| --- | --- | --- | --- |
| `dim_team` | `string` | Нет | `runs`, `measurements` |
| `dim_product` | `string` | Нет | `runs`, `measurements` |
| `dim_run_kind` | `string` с перечислением допустимых значений | Нет | `runs` |
| `dim_pull_request_number` | `integer` | Да | `runs` |

По умолчанию все измерения размещаются только в `runs`. Повторение полей в других таблицах включается явно для потребителей, которым нужны самостоятельные плоские записи.

### Правила профиля

1. Логическое имя измерения соответствует шаблону `[a-z][a-z0-9_]*`. Физическая колонка получает префикс `dim_`; этот префикс зарезервирован для пользовательских измерений. Системные поля переопределять нельзя.
2. Первая версия поддерживает скалярные типы `string`, `integer`, `number`, `boolean` и `datetime`. Для времени используется RFC 3339 с часовым поясом и нормализацией в UTC. Типы коллекций и произвольные выражения отложены.
3. В `source` задаётся ровно один источник: литерал `value`, переменная `env` или именованное значение входного `context`. Контекст передаёт вызывающая сторона; контракт не закрепляет имена конкретной CI-системы.
4. Отсутствующий источник обязательного значения останавливает подготовку анализа. Для необязательного поля результат равен `null`. Пустая строка считается значением и проверяется ограничениями, включая `min_length`.
5. Для строк значения окружения сохраняются без неявной обрезки. Целые принимаются в десятичной записи без дробной части; вещественные — в числовой записи JSON без `NaN` и бесконечностей; логические — как `true` или `false`. Переполнение и нарушение типа являются ошибками даже для необязательного поля.
6. `required: false` делает поле nullable, но не удаляет колонку. Ограничение `enum` проверяется для ненулевого значения после проверки типа.
7. Неизвестные свойства профиля и конфликтующие объявления являются ошибками. Переопределение профиля флагами, наследование и скрытые значения по умолчанию в первой версии не вводятся.
8. Схема строится без чтения исходников и значений окружения. Значения запуска разрешаются один раз до анализа и затем не меняются.

### Составление итоговой схемы

Построение проходит последовательно: проверка версии контракта, проверка возможностей сборщика, проверка профиля, добавление измерений, разворачивание явно запрошенных повторений, проверка конфликтов и выпуск схем ресурсов.

Набор содержит машиночитаемые типы, обязательность, первичные и внешние ключи. Для JSON-записей предлагается JSON Schema, для межтабличных связей — каталог ресурсов и ключей. Конкретный диалект схем должен быть зафиксирован до реализации валидатора; перевод в ограничения отдельного коннектора остаётся задачей интеграции.

`schema_id` вычисляется из канонического описания выходных схем и ключей. Значения тегов, время запуска, порядок ключей входного JSON и имена переменных окружения в него не входят. При одинаковой выходной схеме смена `TEAM_NAME` на другой источник значения не меняет `schema_id`, но меняет эффективную конфигурацию профиля.

Алгоритм канонизации, состав хешируемых данных и тестовые векторы должны быть одинаковыми для всех реализаций. До их фиксации нельзя объявлять идентификаторы схем разных SDK совместимыми.

Версия методики метрики хранится отдельно от версии структурной схемы: изменение формулы может менять смысл значений без изменения колонок. Аналогично, изменение `dim_team` с `payments` на `billing` меняет данные, а смена типа этой колонки меняет схему.

## Идентичность и полнота снимка

Каждый запуск относится к одному сборщику. `run_id` создаётся до анализа и уникален независимо от машины и выбранного хранилища. Повторное чтение или доставка готового результата сохраняет его идентификатор. Повторный анализ, даже той же ревизии, получает новый идентификатор.

Для объединения нескольких сборщиков в одну корпоративную проверку можно объявить общее измерение, например `collection_id`. Совпадение этого значения не делает разные запуски одним запуском и не объединяет автоматически их сущности.

Сборщик публикует полный снимок своей объявленной области анализа. Состояние анализа принимает значения `complete`, `partial` или `failed`; отдельно указываются полнота локальных метрик, разрешения связей и других объявленных возможностей. Полнота означает выполнение заявленного режима, включая его ограничения, а не абсолютное знание всех зависимостей программы.

Запуск содержит количество выбранных, успешно обработанных и ошибочных файлов или иных входных единиц. Если обход не завершён и общее число неизвестно, это значение остаётся неизвестным. Ошибочная сущность сохраняется в `entities` со своим состоянием, даже когда метрики для неё получить нельзя.

Отсутствие сущности в новом снимке само по себе не означает удаление из проекта. Сопоставлять состав можно при совместимых областях анализа и достаточной полноте обоих запусков. Изменение фильтров, неполный обход и ошибка разбора должны отличаться от удаления. Базовый контракт не объявляет файловую публикацию потоком CDC.

## Публикация и повторная доставка

В файловом профиле каждый ресурс содержит JSONL-записи одной схемы. Логи и текстовая сводка в ресурсы не попадают. Пустые ресурсы имеют схему и нулевое число записей.

Пример организации локального пакета:

```text
<run_id>/
  manifest.json
  schemas/
  runs.jsonl
  entities.jsonl
  metric_definitions.jsonl
  measurements.jsonl
  relations.jsonl
  cycles.jsonl
  cycle_members.jsonl
  diagnostics.jsonl
```

Манифест перечисляет ресурсы, пути к схемам, ключи, число записей и контрольные суммы файлов. Он также содержит идентификатор запуска, версию контракта, `schema_id` и состояние анализа. Набор должен быть самодостаточным: определения используемых метрик и схемы доступны вместе с данными.

Пакет собирается в промежуточном месте и становится доступным как готовый только после проверки. На локальной файловой системе можно использовать переименование каталога в пределах одной файловой системы. Для удалённой публикации способ обнаружения готового набора определяет интеграция компании; она должна учитывать отсутствие общей транзакции над несколькими объектами.

Готовый артефакт неизменяем. Исправленные результаты публикуются новым запуском. Порядок строк в ресурсе фиксируется при создании артефакта, чтобы повторное чтение сохраняло контрольные суммы. Побайтовое равенство разных запусков не требуется.

Завершение публикации не означает завершения анализа без ошибок. Можно корректно опубликовать результат `partial` или диагностический результат `failed`. Если не удалось сформировать валидный пакет, он не объявляется готовым. Внезапный обрыв процесса может вообще не оставить пригодного результата.

Повторная доставка использует исходные ключи записей. Выбранная интеграция обеспечивает устранение дублей через upsert или другую явно проверенную стратегию. Контракт предоставляет данные для этой стратегии, но не обещает exactly-once в произвольном хранилище.

Обычный файловый коннектор может не понимать манифест и загружать таблицы независимо. Поэтому интеграция отдельно проверяет готовность данных в целевом хранилище по составу ресурсов, количествам и связности ключей. До завершения такой проверки запуск не должен попадать в представление готовых данных для BI.

Инкрементальная доставка означает обнаружение новых артефактов, а не сравнение SHA коммитов или часов машин. Коннектор хранит собственное состояние загрузки и учитывает поздние поступления. Ревизия, время анализа и время доставки имеют разные значения.

## Совместимость и эволюция

Контракт, корпоративный профиль, методики метрик и структурная схема версионируются раздельно. В артефакте сохраняются их идентификаторы, а также версия сборщика и эффективные настройки, необходимые для интерпретации результата.

Смена типа, ключа, единицы измерения или смысла поля требует явного решения о совместимости. Добавление необязательной колонки также меняет `schema_id`; допустимость объединения таких записей в одной физической таблице проверяет интеграция. Разные схемы нельзя молча смешивать и отдавать на угадывание типов по первому файлу.

Базовая политика первой версии — отдельные наборы для разных `schema_id`. Интеграция может объединять совместимые версии после явного сопоставления схем. Новая неподдерживаемая версия контракта отклоняется с понятной диагностикой.

## Проверка соответствия

Независимый комплект проверки должен принимать описание сборщика, профиль и готовый пакет. Для проверки значений из окружения или контекста используются отдельные тесты построения схемы и разрешения входных данных.

Комплект включает следующие группы проверок:

- структура схем, типы, обязательные поля, уникальность и внешние ключи;
- определения всех опубликованных метрик, допустимые состояния и отсутствие нечисловых значений;
- построение одинаковой схемы из эквивалентных профилей и повторение измерений без расхождений;
- отсутствие обязательного значения, ошибочный тип, неизвестное свойство и конфликт имени;
- контрольные суммы, количества, пустые ресурсы и состояния неполного анализа;
- повторное чтение артефакта с теми же идентификаторами;
- смена профиля, методики и версии контракта с ожидаемым решением о совместимости.

Эталонные примеры должны включать хотя бы два стека и два корпоративных профиля. Второму сборщику не требуется использовать код FtaQl. Общая схема считается пригодной к стабилизации, когда его результаты проверяются тем же валидатором и загружаются той же интеграцией по опубликованным схемам.

## Основания для файлового профиля

Файловая публикация позволяет начать с существующих средств доставки. Airbyte S3 поддерживает структурированные файлы, несколько потоков и инкрементальную загрузку, но не репликацию удалений. Fivetran предоставляет разные режимы обработки файлов, от которых зависит организация таблиц. dlt поддерживает чтение JSONL, CSV и Parquet из локальных и облачных хранилищ. Эти возможности обосновывают выбор первого профиля, а фактическая совместимость требует испытаний конкретной интеграции.

- [Airbyte S3 и поддерживаемые режимы загрузки](https://docs.airbyte.com/integrations/sources/s3).
- [Fivetran и правила загрузки файлов](https://fivetran.com/docs/connectors/files).
- [dlt и чтение файловых источников](https://dlthub.com/docs/dlt-ecosystem/verified-sources/filesystem).

Singer описывает обмен через `SCHEMA`, `RECORD` и `STATE`; Airbyte имеет собственный протокол источников. Адаптер к одному из этих протоколов может читать общий пакет, не меняя устройство сборщика.

- [Спецификация Singer](https://hub.meltano.com/singer/spec/).
- [Протокол Airbyte](https://docs.airbyte.com/platform/understanding-airbyte/airbyte-protocol).

Для описания ресурсов и ключей стоит проверить профиль на основе [Data Package](https://datapackage.org/standard/data-package/) и [Table Schema](https://datapackage.org/standard/table-schema/). Такой дескриптор помогает проверять набор, но его наличие не означает, что любой файловый коннектор прочитает его автоматически.

## Решения перед стабилизацией первой версии

Описанный проект фиксирует границы ответственности и ожидаемое поведение. До выпуска стабильного контракта остаётся:

1. Выпустить полные машиночитаемые схемы профиля, возможностей, ресурсов и манифеста; выбрать диалект JSON Schema.
2. Зафиксировать канонизацию схемы, алгоритм `schema_id`, правила построения ключей записей и тестовые векторы.
3. Согласовать начальный каталог общих метрик и определить, какие методики остаются специфичными для сборщиков.
4. Проверить модель измерений и корпоративных полей на двух независимых сборщиках.
5. Проверить пакет через dlt и второй независимый инструмент доставки, включая повторы и частичную загрузку.
6. По результатам испытаний решить, нужен ли профиль Data Package и когда добавлять Parquet. REST API и адаптеры конкретных протоколов вводить под подтверждённые сценарии.
