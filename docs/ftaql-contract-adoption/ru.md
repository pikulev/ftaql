# План приведения FtaQl к контракту системы анализа кода

Статус: проект плана для обсуждения. Исходное состояние проверено по реализации в коммите `1c3fd31`. Новые API, команды, форматы и этапы ниже являются предложениями. Документ подготовлен на русском для внутренней работы.

FtaQl должен стать самостоятельным сборщиком аналитических данных для TypeScript и JavaScript, соответствующим [общему контракту системы анализа кода](../code-analysis-contract/ru.md). Контракт существует отдельно от реализации: авторы сборщиков для других стеков используют его спецификацию, схемы и проверки соответствия.

Для FtaQl переход означает сохранение анализа JS/TS, появление полного отчёта о запуске и публикацию данных по схеме, построенной с учётом корпоративного профиля. SQLite остаётся доступным локальным способом хранения. Доставку в корпоративные хранилища выполняют выбранные компанией внешние инструменты.

## Ожидаемый результат

Пользователь задаёт проект, настройки анализа и профиль данных. FtaQl проверяет конфигурацию, показывает итоговую схему по запросу, разрешает значения дополнительных измерений и выполняет анализ. После анализа он выпускает проверяемый пакет данных с диагностикой и признаками полноты.

Один и тот же результат можно опубликовать в файловом формате и сохранить в SQLite с общей внешней идентичностью запуска. Повторная доставка файлов не требует повторного анализа. Изменение команды или продукта в метаданных не меняет аналитическую методику.

Успешный переход проверяется двумя корпоративными профилями, независимым сборщиком другого стека и внешней загрузкой. Разделение ответственности считается рабочим, когда новый сборщик подключается по общему контракту без изменения кода анализа TS/JS.

Однако текущий экспорт связей фильтрует цели, отсутствующие в `findings`, а значит, восстановить полную диагностику из готовой базы нельзя. ## Границы внутри FtaQl

Предлагается выделить четыре ответственности:

```text
настройки анализа ────────────→ анализ JS/TS ───────→ полный отчёт
                                                     │
профиль компании → построение схемы → значения запуска │
                                      └──────────────┤
                                                     ├→ пакет данных
                                                     ├→ SQLite
                                                     └→ результат проверки порогов
```

Парсер SWC, разрешение импортов, цикломатическая сложность и Halstead остаются внутри реализации FtaQl. Общий контракт не должен зависеть от типов SWC, `FileData` или схемы SQLite.

Первую реализацию можно организовать модулями существующего crate. Отдельный пакет со схемами, примерами и проверками соответствия должен быть пригоден для использования другими сборщиками. Выделять общий движок разбора языков для этой задачи не требуется.

## Полный отчёт анализа

Новый отчёт должен содержать контекст запуска, выбранные входные единицы, состояния их обработки, метрики, сведения о разрешённых и неразрешённых связях, диагностику и полноту отдельных частей анализа.

Для получения такого отчёта потребуется изменить путь ошибок. В новом API ошибки обхода, чтения и разбора возвращаются структурированно. Восстановимая ошибка отдельного файла сохраняет его в отчёте; ошибка, не позволяющая продолжить запуск, завершает анализ с явным состоянием. Возможность сформировать диагностический пакет зависит от того, насколько далеко прошла подготовка.

Предлагается добавить API полного отчёта, сохранив сигнатуры `analyze_project` и `analyze_module` через совместимый слой. Старый результат остаётся проекцией данных для существующих потребителей. Новый API не должен вызывать `process::exit`; этим управляет CLI. Поведение старого API при ошибках нужно отдельно зафиксировать тестами и описать при выпуске изменения.

Текущие два прохода повторно читают исходники. Для воспроизводимого снимка нужно либо работать с подготовленным неизменяемым checkout, либо использовать согласованный набор считанных исходников. Проверка хешей между чтениями может обнаруживать изменения, но не заменяет согласованный снимок. Выбор способа нужно проверить по памяти и времени на реальном проекте.

## Сохранение семантики метрик

До рефакторинга нужно зафиксировать действующие результаты на эталонных проектах. Затем описать методики в каталоге метрик: уровень измерения, правила учёта конструкций, единицы, формулы и допустимую агрегацию.

Например, текущий Cyclo начинает подсчёт с единицы на весь модуль. Перенос к сумме сложностей функций изменит методику и не должен происходить незаметно при добавлении экспорта. Правила подсчёта операторов и операндов Halstead также принадлежат версии методики FtaQl.

При публикации значения проверяются на конечность и соответствие типу. Для невычислимого значения формируется состояние и диагностика. Исправление обнаруженной формулы оформляется отдельным изменением методики, чтобы разницу между запусками можно было объяснить.

Возможности проекта и одиночного файла объявляются отдельно. WASM сохраняет свой текущий интерфейс; без проектного контекста он не должен объявлять поддержку разрешения межфайловых связей. Его включение в публикацию общего контракта можно выполнить отдельным этапом.

## Корпоративный профиль

Формат профиля определяется общей спецификацией. FtaQl должен принимать профиль отдельным файлом, чтобы его можно было использовать с другим сборщиком. Существующий `ftaql.json` продолжает описывать настройки анализа JS/TS; связь между двумя конфигурациями задаётся явно при запуске.

Построитель схемы принимает профиль и объявленные возможности FtaQl. Он выдаёт схемы таблиц, описание ключей и `schema_id` до анализа исходников. Отдельный шаг получает значения из литералов, окружения или входного контекста и проверяет их по профилю.

Поле `team` должно давать одну и ту же колонку `dim_team` и одинаковые правила проверки во всех сборщиках. Если профиль требует `team`, отсутствие значения останавливает подготовку. Необязательное поле остаётся в схеме с `null`, а неверный тип не маскируется отсутствующим значением.

Если профиль предписывает повторять измерение запуска в `measurements`, экспорт копирует разрешённое значение в каждую запись. Сам анализатор не читает окружение повторно для отдельных файлов. Так метаданные одного запуска остаются согласованными даже при параллельном анализе.

Для первой версии достаточно скалярных полей и явного выбора источника. Выражения, шаблонизаторы, наследование профилей и переопределение отдельных полей через CLI стоит добавлять только после проверки базового механизма.

## Публикация результатов

Первый экспортёр создаёт JSONL-пакет по общему контракту. Один ресурс содержит записи одной схемы; зависимости и циклы преобразуются в записи с ключами сущностей. Корпоративные измерения включаются в итоговую схему и данные согласно профилю.

Пакет создаётся в промежуточном каталоге. После записи проверяются схемы, ключи, количества и контрольные суммы, затем каталог публикуется как готовый. На ошибке экспорта готовый пакет не появляется. Повторная доставка использует уже созданные файлы и не запускает анализ заново.

Манифест должен различать корректно завершённую публикацию и полноту анализа. Результат с ошибкой разбора может быть опубликован как `partial`; нарушение порога качества может сопровождать полностью выполненный анализ. Ни одно из этих состояний не равно ошибке записи файлов.

Человеческая сводка и диагностические логи направляются в stderr в машинном режиме. Для больших результатов основной путь — каталог файлов; если позже появится потоковый stdout, нужно определить формат завершения и поведение при обрыве. Node API не должен буферизовать весь набор данных ради возврата строки.

Перенос пакета в S3, другое объектное хранилище или корпоративный каталог выполняет внешний конвейер. В составе проекта нужны примеры такой интеграции и схема размещения ресурсов, пригодная для выбранного коннектора. Универсальный набор драйверов БД в FtaQl для этого не требуется.

## SQLite и существующие API

Режим `--db` и текущий Node API должны продолжить работать. Для новой публикации предлагается отдельный метод Node API, возвращающий путь к артефакту, внешний `run_id`, `schema_id` и состояние запуска. Его точное имя определяется при проектировании API.

SQLite получает внешний идентификатор запуска наряду с существующим локальным числовым ключом. Если один анализ сохраняется двумя способами, оба представления ссылаются на один внешний запуск. Повторный вызов сохранения полного отчёта должен иметь документированное поведение: для нового API предпочтительна идемпотентная запись с проверкой совпадения содержимого.

Корпоративные поля не должны требовать произвольного `ALTER TABLE` основной таблицы при каждом профиле. Для локального SQLite предлагается хранить схему и типизированные значения измерений в отдельных таблицах. Плоское представление для экспорта строится из них по профилю. Физическое устройство базы может отличаться от внешней схемы, пока обратное чтение сохраняет типы и состояния.

Состояния невычисленных метрик тоже требуют изменения хранения: текущие обязательные числовые колонки не выражают ошибку или неприменимость. Миграция должна сохранять эти состояния отдельно от значений. Подстановка нулей ради выполнения ограничения `NOT NULL` недопустима. Ошибочные сущности также должны сохраняться независимо от наличия строки с успешными метриками.

Смена SQLite-схемы требует миграции существующих баз, проверки сохранности истории и сохранения прежних запросов там, где заявлена совместимость. `CREATE TABLE IF NOT EXISTS` само по себе не выполняет миграцию имеющихся таблиц.

Исторические записи не содержат всех новых сведений. При их экспорте неизвестная полнота остаётся неизвестной. Внешние идентификаторы нужно один раз назначить и сохранить вместе с происхождением; нельзя создавать новый идентификатор при каждом экспорте старой записи. Восстановить пропущенные ошибки и неразрешённые импорты без повторного анализа невозможно.

После отделения SQLite в Cargo feature старую конфигурацию сборки можно оставить конфигурацией по умолчанию. Дополнительно требуется проверить нативный анализ и файловый экспорт без SQLite, а также существующую сборку WASM без проектных зависимостей.

## Предлагаемый интерфейс CLI

Ниже показаны варианты будущего интерфейса. Эти команды пока не реализованы.

```text
ftaql describe --profile company-analysis.json
ftaql schema --profile company-analysis.json --output-dir ./schemas
ftaql analyze ./project --profile company-analysis.json \
  --project-id payments/frontend --revision <commit-sha> \
  --output-dir ./artifacts/analysis
```

`describe` объявляет возможности сборщика. `schema` строит схему без чтения проекта и значений окружения. `analyze` принимает профиль, разрешает значения измерений и публикует результат. Добавление подкоманд должно сохранить существующий вызов `ftaql <project> --db <path>` либо сопровождаться отдельно согласованным изменением совместимости.

Числовые коды завершения нужно закрепить при реализации CLI. Их смысл должен различать следующие случаи:

| Случай | Результат |
| --- | --- |
| Невалидный профиль или обязательное значение отсутствует | Анализ не начинается; ошибка подготовки доступна вызывающей стороне |
| Анализ завершён полностью | Публикуется готовый пакет с состоянием `complete` |
| Ошибка части файлов | Публикуется `partial`, если удалось получить валидный отчёт; отдельный код сообщает о неполноте |
| Невосстановимая ошибка анализа | При наличии достаточного контекста публикуется диагностический пакет `failed`; иначе остаётся ошибка процесса без готового пакета |
| Порог качества нарушен | Пакет публикуется, нарушение записывается отдельно; после этого возвращается код нарушения |
| Экспорт не завершён | Пакет не объявляется готовым; возвращается ошибка публикации |

Если одновременно присутствуют неполнота и нарушение порога, оба состояния остаются в данных. Для единственного кода CLI нужен документированный порядок приоритетов: ошибка публикации, ошибка или неполнота анализа, нарушение порога, успех.

## Этапы реализации и приёмка

### Этап 1 Контракт и эталонные примеры

Подготовить машиночитаемые схемы, правила канонизации, каталог начальных метрик и валидатор. Сформировать два корпоративных профиля и примеры данных TS/JS и второго стека. На этом этапе второй стек может быть представлен вручную подготовленным набором; это проверяет модель, но ещё не доказывает возможность независимой реализации.

Приёмка: эквивалентные профили дают одинаковый `schema_id`; смена значения тега его не меняет; изменение типа меняет. Ошибочные типы, конфликт имён и нарушение внешних ключей отвергаются. Формат профиля не содержит требований к Rust или SWC.

### Этап 2 Полный отчёт FtaQl

Ввести контекст запуска, состояния входных единиц, диагностику и полноту. Отделить проверку порога от завершения процесса и сделать чтение конфигурации строгим в новом пути исполнения. Зафиксировать действующие методики и результаты до изменения конвейера.

Приёмка: эталонные корректные проекты сохраняют результаты; файл с ошибкой разбора остаётся видимым; неразрешённая ссылка имеет состояние; превышение `score_cap` не прерывает формирование отчёта. Ошибки обхода не превращаются в успешный пустой запуск.

### Этап 3 Профиль и файловый экспорт

Реализовать построение схемы, разрешение значений профиля и JSONL-пакет. Добавить новый CLI-путь и Node API. Для SQLite подготовить совместимую миграцию и отделение зависимости от проектного анализа.

Приёмка: один результат экспортируется с двумя корпоративными профилями без изменения метрик; поля и типы соответствуют каждой схеме. Публикация работает без SQLite. Повторное чтение даёт те же ключи и контрольные суммы. Прерванная запись не выглядит готовым пакетом. Старые CLI-вызовы и существующие базы проходят проверки совместимости.

### Этап 4 Внешняя загрузка

Подготовить воспроизводимый пример загрузки через dlt в отдельное тестовое хранилище. Затем проверить тот же контракт через второй независимый инструмент; кандидат — Airbyte S3 Source. Пример должен задавать ключи, обработку схем и проверку готовности всех таблиц.

Приёмка: сохраняются типы, ключи и количества; повторная доставка не удваивает логические записи; поздний запуск не теряется; частичная загрузка не попадает в готовые данные BI. Изменение профиля проходит предусмотренный путь совместимости. Поддержка формата в документации инструмента сама по себе не закрывает этот этап.

### Этап 5 Независимый сборщик

Реализовать небольшой сборщик второго стека по общей спецификации. Go подходит как кандидат для проверки сущностей уровня пакета, но выбор стека можно изменить под реальную потребность. Сборщик должен самостоятельно объявить возможности, применить корпоративный профиль и выпустить результат.

Приёмка: сборщик проходит общий комплект проверок и существующий путь загрузки без изменений анализа TS/JS. Отличия в доступных метриках и уровнях графа выражаются данными контракта. По результатам этого этапа можно стабилизировать первую версию спецификации.

## Набор обязательных проверок

| Сценарий | Ожидаемое свойство |
| --- | --- |
| Два значения `team` при одном профиле | Схема не меняется; значения различаются только в данных |
| Добавление измерения и смена типа | Изменение схемы обнаруживается до загрузки |
| Отсутствующий обязательный тег и неверное число | Подготовка завершается ошибкой без скрытых значений по умолчанию |
| Пустой проект | Валидные схемы, нулевые количества и понятная область анализа |
| Ошибочный файл и неразрешённый импорт | Явные состояния и диагностика; отсутствие ложной полноты |
| Исключение файла конфигурацией | Изменение области анализа отличается от удаления файла |
| Обрыв публикации или загрузки | Неполный набор не объявляется готовым для BI |
| Повторная доставка | Сохраняются идентификаторы и логическое количество записей |
| Поздний запуск и несколько веток | Порядок доставки не подменяет порядок и принадлежность ревизий |
| Изменение формулы метрики | Версия методики объясняет изменение смысла без обязательной смены колонок |
| Второй сборщик и другой профиль | Совместимость определяется контрактом, а не устройством FtaQl |

Для изменений Rust применяются проверки репозитория: `cargo test --all`, `cargo fmt --check`, `cargo clippy --all --all-targets` и сборки затронутых вариантов features. Изменения WASM дополнительно проверяются его тестами и целевой сборкой. Контракт и профили проверяются отдельными тестами схем и примеров; интеграции доставки — реальной загрузкой и повторной загрузкой тестового набора.

Переход на сериализацию по частям не гарантирует уменьшения памяти самого анализа. До обещаний о производительности нужно измерить размер пакетов, время экспорта и пиковую память на репрезентативных проектах, включая стоимость повторения корпоративных полей.

## Что требует решения перед реализацией

Первыми нужно согласовать полные схемы ресурсов, канонизацию `schema_id` и начальные определения метрик. Затем выбрать способ получения согласованного снимка исходников и политику миграции старых SQLite-баз.

Для внешних интеграций требуется выбрать вторую систему доставки и место тестовой публикации. Учётные данные и инфраструктура нужны на этапе испытаний конкретной интеграции; они не должны определять общий контракт или внутренний анализатор.

Работа завершается по этапам с записью фактических результатов проверки. Задачи GitHub и изменения статусов проекта создаются или обновляются отдельным действием после согласования плана. Этот документ сам по себе не означает, что реализация или интеграционная проверка уже выполнена.
